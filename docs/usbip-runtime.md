# Android USB/IP runtime and Windows packaging

Android's existing USB/IP setting adds `usbipMode=1&usbipTls=1` to paired HTTPS launch/resume requests. Missing, disabled or other values leave ordinary streaming unchanged. The Windows stream uses its actual RTSP peer address and launches `tools/usbip-reconnect.exe --watch-tls <numeric peer> <Sunshine PID> <launch ID>` when TLS was negotiated; older clients use `--watch`. USB/IP follows the streaming family without a separate IPv4/IPv6 preference or cross-family fallback. Android exports fixed TCP 3240 and bus `1-1`; the client cannot choose an arbitrary destination or port.

Both ends support LAN IPv4/IPv6 and publicly routed IPv6. Transport selection is automatic: LAN uses the original direct driver path without TLS or a loopback bridge, while cross-network public IPv6 requires negotiated TLS and never falls back to plaintext. LAN eligibility includes RFC1918 IPv4 (normalizing mapped addresses), IPv6 ULA, scoped link-local IPv6, and global IPv6 on a direct local route. Check the route rather than assuming all global-address IPv6 is Internet traffic. TLS capability in a launch query is an offer, not a demand to encrypt LAN traffic. Public IPv4, loopback, multicast, unspecified addresses and unscoped link-local IPv6 remain rejected. Internet IPv6 additionally requires the PC to reach the Android export; hotspot/carrier inbound filtering can still prevent a connection. NAT traversal for public IPv4 is not implemented.

The successful paired launch/resume response advertises `axiUsbIpTls=1` and a fresh 256-bit hexadecimal `axiUsbIpToken`. The host passes the token and the exact already-paired Android certificate to the helper through a bounded inherited stdin pipe, never command-line arguments or logs. Android serves TLS 1.2/1.3 using its existing Moonlight client certificate/key. The Windows TLS client pins that certificate's SHA-256 hash, and Android verifies the 64-byte session token in constant time before processing any USB/IP operation. A malformed negotiated credential disables export rather than silently selecting plaintext. Tokens last only for that stream and change on launch/resume; Android suppresses full launch/resume request/response logging.

The pinned VHCI driver speaks ordinary USB/IP to a helper-owned ephemeral IPv4 loopback listener. The helper bridges those bytes over certificate-pinned TLS to Android, preserving USB/IP URBs, fixed bus identity, device interfaces and cancellation ownership. DEVLIST uses the same authenticated bridge as the real import. The bridge is never exposed on public interfaces and closes after watcher cleanup. With TLS, the real remote IPv6 TCP connection is owned by `usbip-reconnect`, while the kernel connects only to loopback; do not mistake that local driver endpoint for unencrypted public traffic.

Android binds a wildcard address of the streaming family so IPv6 privacy addresses do not cause a listener/source-address mismatch. It authorizes only the negotiated PC source address, in addition to TLS/token checks; link-local checks include Android's own scope ID. Source-address discovery runs off the UI thread, and IPv6 endpoints use `[address%scope]:3240`. Full performance values wrap when too long, including USB/IP status and IPv6 addresses; retain the original panel-height layout. The HUD appends `TLS` for encrypted sessions. Android-version errors are separate from network/negotiation errors. The driver payload is unchanged.

IPv6 source selection can differ from the PC address entered in Moonlight: a stream may target a stable address while reverse USB/IP uses a Windows temporary address. Successful paired launch/resume responses include optional `axiUsbIpHost` for opted-in IPv6 clients. The host queries OS source selection without transmitting a UDP packet. Android applies the numeric same-family peer before enabling its export, retaining network-policy checks and exact address authorization. IPv4, missing/invalid fields and link-local scope handling retain the original peer. Reconnect after a source-address change; never authorize a whole subnet as a privacy-address workaround. A default-source DEVLIST probe being immediately closed while a probe bound to the PC stream address succeeds identifies this mismatch.

The helper is published self-contained for Windows x64, with HIDMaestro 2.1.0 and its USB/IP payload embedded. No installed .NET runtime or development SDK path is required. `--check-sdk` validates the embedded interfaces without installing a driver. `--prepare-driver` invokes the pinned SDK's `EnsureInstalled` policy: install missing host-controller support, preserve supported existing transports, and apply eligible SDK-managed upgrades when Windows allows it. It does not run a full usbip-win2 installer or install its root-hub filter.

The Windows setup script runs driver preparation before starting Sunshine's service. Preparation failures are logged and ordinary Sunshine installation/streaming can continue. Portable use prepares the transport when the opted-in session starts; first-time driver installation needs administrator privileges. The existing shared USB/IP driver remains installed on StarCore uninstall because other programs may use it.

If a separate USB/IP uninstaller removes the active VHCI driver while a root hub is still open, Windows can leave `ROOT\USB\0002` present with a NULL driver and a pending reboot. A generic PnP status of `OK` or problem code zero does not establish that the controller has a driver: also check its driver binding and whether the SDK can open it. `setupapi.dev.log` records the uninstall, `PNP_VetoOutstandingOpen`, and `Reboot needed to complete driver update`. Finish that requested Windows restart before preparing the bundled driver again. The SDK deliberately refuses to create a duplicate controller beside this stale device; changing IPv4/IPv6 or reinstalling the Android APK cannot repair this state.

Compare the actual last boot time with the uninstall time before recommending another restart. A NULL-driver node can persist after a completed restart. In the verified local repair, stop StarCore and its own helper processes, back up the device registration, confirm the exact node has `ROOT\USBIP_WIN2\UDE` hardware identity and no `Driver` or `Service` binding, then remove only that stale node with `pnputil /remove-device`. Run the bundled `usbip-reconnect.exe --prepare-driver` as administrator and restore the StarCore service. This successfully restored the signed 0.9.8.1 controller without another reboot. Never apply this removal to a healthy, bound controller or to unrelated USB devices.

Each stream owns a manual-reset cancellation event and one helper process. Disconnect signals the event; parent exit is also detected. The helper cancels pending attempts and detaches only its own imported location/port. An import already present when the helper starts is left alone. Replug readiness uses bounded DEVLIST probes before retrying, preserving the existing fast reconnect behavior and virtual-controller fallback until the physical import is confirmed.

Logs are appended to `config/usbip.log`; Sunshine's main log records importer startup and missing helper errors. Android keeps reporting the endpoint and handoff status in the full performance overlay. There is no new menu option. Older Android builds without the launch flag require their former manual importer; update both ends to use automatic session startup.

The Windows Web UI exposes read-only `GET /api/usbip/driver/status` and authenticated, CSRF-protected `POST /api/usbip/driver/repair`. Troubleshooting shows controller health and an explicit repair button; the homepage only warns about detected failures, leaving unused/missing USB/IP installations quiet. Repair is blocked while streams are active, serialized per process and by the helper's named mutex, and uses only the fixed bundled helper. Administrator cancellation, failed preparation and an explicit Windows reboot request are separate results. No automatic reboot is performed. The elevated helper backs up and rechecks each exact USB/IP root identity before removing an unbound node; healthy or rebound controllers are preserved. Preparation uses the pinned SDK. Diagnostic inspection never installs a driver, and repair progress can be resumed by refreshing the page.

Verification includes native address-policy tests; IPv4/IPv6 DEVLIST fixtures; real TLS fixtures for valid identity, wrong certificate, wrong token and idle cancellation; and Android parsing, token and compatibility tests. On 2026-11-07, OPPO and Windows first imported a physical DS5 over LAN IPv6, then repeated import with TLS. A cross-network test with the PC on its home router and OPPO on a phone hotspot established TLS to a different globally routed IPv6 prefix, imported on VHCI port 1, and enumerated healthy USB composite, HID and DualSense media devices. Public-IPv6 hotplug subsequently detached and reimported successfully. Individual controller speaker/microphone playback was not separately exercised in this validation.
